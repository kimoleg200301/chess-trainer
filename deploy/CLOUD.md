# Облачный запуск и последующий перенос на VPS

Для этого проекта выбран **Render**: два независимых Docker-сервиса и обычный PostgreSQL 17. Браузер обращается к одному HTTPS-адресу фронтенда; nginx передаёт `/api` приватному FastAPI. Движок Stockfish работает внутри контейнера API. PostgreSQL и API не имеют публичного входа.

Файл [render.yaml](../render.yaml) описывает все три ресурса. Это подготовленная конфигурация, а не подтверждение состоявшегося размещения. Для запуска нужны Git-репозиторий, аккаунт Render и подключённый способ оплаты. В текущей рабочей среде доступ к аккаунту Render не настроен.

Это оценка для маленького личного приложения. Она не включает налоги, платные превышения трафика и сборок, дополнительные ресурсы или изменение тарифов. На странице тарифов указан 1 GB SSD в составе PostgreSQL и расширение по $0.30/GB. В Blueprint явно установлен `diskSizeGB: 1`, чтобы не получить больший диск по умолчанию. Рост диска и автоматические превью отключены. 512 MB для API — стартовая конфигурация; при росте нагрузки сначала проверить память и время анализа Stockfish.

Источник: [Render Pricing](https://render.com/pricing), [актуальные идентификаторы планов и параметры Blueprint](https://render.com/docs/blueprint-spec). Старые названия `starter` и `basic-256mb` в конфигурации не используются.

Railway тоже подходит для этих Docker-образов и PostgreSQL. У Hobby минимальный расход $5 в месяц с включёнными $5 использования, далее оплата ресурсов. Это может быть дешевле, но $5 не означает фиксированную цену всего приложения. Для данного проекта Render выбран ради декларативного развёртывания и понятной стоимости трёх постоянно работающих ресурсов. Источник: [Railway Pricing](https://railway.com/pricing).

## Развёртывание

1. Разместить код в своём GitHub/GitLab-репозитории. `.env`, дампы базы, пароли и токены не должны попасть в Git.
2. Открыть [Render Dashboard](https://dashboard.render.com/), выбрать **New → Blueprint**, подключить репозиторий и корневой `render.yaml`.
3. Проверить три ресурса, регион Frankfurt и платные планы. В поле `AUTH_PASSWORD` задать уникальный пароль минимум из 12 символов; логин — `trainer`. Пароль вводится в Render, не в исходный код или переписку.
4. Создать Blueprint. Миграции, загрузка задач и создание пользователя выполняются при старте API. Строка подключения PostgreSQL и адрес приватного API передаются через ссылки между ресурсами.
5. Открыть адрес сервиса `tactics-web`, войти и решить задачу. Проверить `/api/health`: база должна отвечать, `engine_available` должен быть `true`.
6. После создания убедиться, что переменная `PUBLIC_HOST` у API содержит домен `tactics-web` без схемы. Blueprint берёт его из `RENDER_EXTERNAL_HOSTNAME`. При собственном домене дополнительно задать `ALLOWED_ORIGINS=https://ваш-домен` у API и перезапустить его.

Сборки запускаются из Dockerfile. Оба сервиса используют корень репозитория как Docker context. Встроенные проверки готовности не заменяют первую проверку входа, решения, статистики и работы движка.

Автоматическая публикация по коммиту отключена (`autoDeployTrigger: off`), поэтому обновление запускается через **Manual Deploy** после проверки кода. При обновлении сначала развернуть API, затем фронтенд, сохраняя совместимость API.

Конфигурация `PUBLIC_HOST` содержит ссылку на публичный hostname фронтенда; `API_UPSTREAM` — ссылку на приватный `hostport` API. Это ссылки на свойства ресурсов, без передачи авторизационного секрета в браузер. Подробности: [переменные окружения и межсервисные ссылки](https://render.com/docs/blueprint-spec), [приватные сервисы](https://render.com/docs/private-services).

## Резервные копии

Платный Render Postgres поддерживает восстановление на момент времени; на Hobby окно составляет три дня. Для независимой копии периодически создавать **Recovery → Create export** и скачивать архив. Экспорты Render хранятся семь дней, поэтому нужные долговременные копии следует хранить отдельно. Источник: [Render Postgres Recovery and Backups](https://render.com/docs/postgresql-backups).

База содержит пользователей, сессии и прогресс, поэтому её дампы нужно хранить как приватные данные. В Git они не включаются.

## Перенос на собственный VPS

1. Подготовить Linux VPS с Docker Compose и доменом; развернуть тот же Git-коммит и конфигурацию Compose из корневого README.
2. Использовать PostgreSQL **17** — ту же основную версию, что задана в Render. Контейнеры фронтенда и API собираются из тех же Dockerfile, поэтому приложение не нужно переписывать.
3. Остановить новые занятия на старом адресе, сделать финальный логический экспорт PostgreSQL и сохранить его вне сервера.
4. Восстановить экспорт в **пустую** PostgreSQL на VPS через `pg_restore --no-owner --no-acl`, запустив клиент той же версии. Для архива Render `.dir.tar.gz` предварительно распаковать каталог. Не запускать bootstrap/seed до восстановления: база должна оставаться пустой.
5. Задать новый `DATABASE_URL`, `COOKIE_SECURE=true` и точный `ALLOWED_ORIGINS=https://ваш-домен`. Перенести `AUTH_USERNAME` и `AUTH_PASSWORD` через защищённые настройки окружения. При совпадении пароля существующий хеш останется в базе; другой `AUTH_PASSWORD` намеренно изменит пароль при старте и отзовёт прежние сессии.
6. Запустить API и фронтенд, проверить вход, статистику, новую задачу, сохранение результата и Stockfish. После проверки перевести DNS и проверить HTTPS на новом адресе.
7. Отключать платные ресурсы Render только после проверки новой базы и сохранения резервной копии.

На VPS потребуется собственное расписание резервных копий и обновлений. Для небольшого личного тренажёра разумно начать с 2 GB RAM и одного одновременно выполняемого анализа Stockfish; окончательный размер сервера выбирать по фактическому потреблению.
